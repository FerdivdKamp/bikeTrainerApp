# Android app options for ErgTrainer

Reviewed 2026-10-25. This is a decision note, not a framework choice or an implementation task. The earlier [`prompt_next_version.md`](prompt_next_version.md) is a Flutter-first backlog; its platform choice remains a proposal.

## Goal and current baseline

The desired new target is an Android phone and tablet app for indoor cycling. A later Windows UI migration is possible, but the existing WinForms app should remain usable while Android is proved on real hardware. Today Windows has BLE trainer and HRM telemetry, ERG session control, charts, local activity journals, and Garmin FIT export. It targets `net8.0-windows10.0.19041.0` and x64; its WinForms UI and Windows BLE implementation cannot simply be packaged as an Android app. The FIT recording changes are still local working-tree changes as of this review, and a physical ride plus Garmin Connect import remain to be checked.

The first Android decision is **what the first APK must do**: display-only telemetry, or run an ERG workout and save a FIT activity. A second decision is whether a ride must continue when the screen locks or the app is backgrounded. These choices affect BLE lifecycle and Android service design more than the UI framework does.

## Work required with any route

1. **Prove the actual trainer and HRM on Android.** Scan, connect to both devices, discover GATT services, subscribe to notifications, decode power/cadence/speed/heart rate, handle Bluetooth off and permission denial, then disconnect and reconnect cleanly. Android 12+ requires runtime `BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT` permissions for these operations; older Android versions have different location requirements. [Android Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions), [BLE overview](https://developer.android.com/develop/connectivity/bluetooth/ble/ble-overview).
2. **Check trainer control separately from telemetry.** Port the supported Tacx FE-C-over-BLE command and response sequence only after reading the Windows implementation and recording sanitized packet examples. Test a modest ERG target while pedaling: a successful GATT write alone does not show that resistance changed. Keep Simulation slope control out of scope until its physical behavior is verified.
3. **Define portable behavior and data.** Specify units, UTC timestamps, missing values, timer pause/resume, disconnect gaps, block boundaries, and safe ERG limits. Keep sanitized BLE payloads with expected decoded values. Decide whether Android should read Windows `.ergsession.json` files and whether its activity journal must match the current `.jsonl` file; the journal does not yet have a versioned cross-platform schema. Preserve existing user recordings.
4. **Design for phone and tablet space.** Show large live values and controls during a ride, with a layout that uses available width rather than a fixed phone/tablet label. Test portrait, landscape, and tablet split-screen or resizing. [Flutter large-screen guidance](https://docs.flutter.dev/ui/adaptive-responsive/large-screens), [adaptive design](https://docs.flutter.dev/ui/adaptive-responsive/best-practices).
5. **Record and export on Android.** Write samples as the ride proceeds, retain pause/disconnect timing, and finalize a FIT **Activity** file from measured data. Validate its structure with the FIT SDK and manually import it into Garmin Connect. Garmin publishes official encoders for C# and Java, but not Rust or Dart; using one on Android, or validating another encoder, is an implementation choice. Use Android app storage for working files and an explicit save/share flow for the FIT file; Android's document picker can create a user-selected file without silently overwriting an existing one. [Garmin FIT SDKs](https://developer.garmin.com/fit/get-the-sdk/), [Android document storage](https://developer.android.com/training/data-storage/shared/documents-files).
6. **Decide the ride lifecycle.** A foreground-only first APK is simpler, but it must say what happens on screen lock or app switch. A continuous ride while backgrounded needs an Android-specific design, such as a `connectedDevice` foreground service or companion-device approach, plus tests for process death and reconnection. [Android BLE background guidance](https://developer.android.com/develop/connectivity/bluetooth/ble/background).
7. **Package and test on devices.** Choose supported Android versions and architectures, install on a real phone and tablet, and test a long ride, pauses, sensor loss, no-HRM ride, export, and import. A distributable APK needs a deliberate signing and update plan; Play distribution has its own app-bundle path. Keep signing keys and device identifiers out of the repository. [Flutter Android release guide](https://docs.flutter.dev/deployment/android), [Android app signing](https://developer.android.com/studio/publish/app-signing).

## Implementation routes

| Route | Advantages | Costs and risks | Windows path |
| --- | --- | --- | --- |
| **Native Android: Kotlin + Compose** | Direct access to Android BLE, permissions, services, and Garmin's Java FIT SDK. Few language bridges for the first Android APK. | New UI and application logic; portable behavior must be specified and tested separately from C#. | Keep WinForms. A later unified Windows UI would be a separate rewrite. |
| **Flutter: Dart UI and application logic** | One responsive UI technology can serve phones, tablets, and potentially Windows. Flutter supports Android and Windows desktop. | WinForms and C# BLE code must be ported. BLE plugin capabilities must be checked against Tacx notifications and control; custom Kotlin/Windows native code may still be needed. Official Garmin FIT SDK is not available for Dart. | Add Windows after Android works, then compare feature parity before replacing WinForms. |
| **.NET MAUI: C# UI and shared logic** | Some hardware-independent C# models, calculations, and tests may be reusable. MAUI officially targets Android and Windows. Existing FIT C# package deserves a compatibility trial. | WinForms UI still needs rebuilding in MAUI/WinUI; Windows and Android BLE transports still need separate validation. Shared C# does not remove Android lifecycle work. | Potential single C# app, but replacing the current Windows UI is a real migration. |
| **Flutter UI + Rust core** | Rust could share pure decoding, session timing, and file logic between Android and Windows. `dart:ffi` and `flutter_rust_bridge` support the integration. | Dart, Rust, and Android/Windows native build layers increase setup and debugging work. BLE permissions and lifecycle remain platform-specific. There is no official Garmin Rust FIT SDK. | Potential shared core and Flutter UI after Android proves the bridge and BLE path. |
| **Rust UI + Rust core, for example Slint** | One main implementation language across Android and Windows; Slint supports both. | More integration work for a first Android APK. Rust BLE Android support must be verified against a specific library version and the actual trainer; `btleplug`'s published crate docs and repository describe Android support differently. FIT encoding also needs a validated non-official Rust path or native bridge. Review Slint's license before distribution. | Replace WinForms only after the Android hardware and packaging path is proven. |

Sources for the route comparison: [Flutter desktop](https://docs.flutter.dev/platform-integration/desktop), [Flutter native code](https://docs.flutter.dev/platform-integration/bind-native-code), [Flutter platform channels](https://docs.flutter.dev/platform-integration/platform-channels), [flutter_rust_bridge](https://github.com/fzyzcjy/flutter_rust_bridge), [.NET MAUI platforms](https://learn.microsoft.com/en-us/dotnet/maui/supported-platforms?view=net-maui-10.0), [Slint Android](https://docs.slint.dev/latest/docs/slint/guide/platforms/mobile/android/), [Slint licensing](https://slint.dev/faqs), [`btleplug` repository](https://github.com/deviceplug/btleplug), [`btleplug` crate docs](https://docs.rs/btleplug/latest/btleplug/).

## Recommendation and decision gates

**Recommended first step:** complete the Windows test ride and Garmin import, then make a small Android BLE proof of concept before choosing an app framework. A minimal Kotlin GATT probe is a practical way to learn whether the phone can receive both sensors and control the trainer; that work could later become a Flutter platform component, or remain a reference for another route. Do not start a full UI port before this hardware result.

If the Android BLE path works, compare **Flutter/Dart** and **.NET MAUI/C#** with one phone-and-tablet workout screen and a small FIT export trial. Flutter is the leading option if a shared future UI is the main goal; MAUI is worth a prototype if reusing C# domain logic matters more. Add Rust only when a specific shared core or Rust-first product goal justifies the bridge and build cost. A pure Rust UI is possible, but it should pass a trainer BLE and FIT export spike first. This is a recommendation for what to test, not a decision to adopt any route.

While the Windows app remains in use, move it to .NET 10 as a separate maintenance change. .NET 8 support ends on 2026-11-10; .NET 10 LTS runs through 2028-11-14. That upgrade is not a prerequisite for Flutter or Rust. [Microsoft .NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy).

**Choose a route when:** the target Android phone/tablet and OS versions are known; scan/connect/notify/reconnect and any required ERG write have worked on a real trainer; foreground versus screen-locked rides are decided; a FIT sample validates and imports; and the UI prototype is comfortable on both phone and tablet. Record measured results and remaining limitations, rather than treating a build or emulator run as hardware proof.
